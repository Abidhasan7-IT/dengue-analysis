# Dengue Risk Assessment — Flask and Streamlit apps

An explainable ML web app for the Dhaka dengue dataset: a model dashboard
(accuracy, ROC, confusion matrix, feature importance, dataset charts) and a
patient-assessment form that returns a risk score plus the factors behind it.

## Setup

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
python -m pip install -r requirements.txt

python train_model.py           # trains the model, writes ./model/*.pkl + metrics.json
python app.py                   # starts the server
# Or run the Streamlit version:
streamlit run streamlit_app.py
```

Open **http://127.0.0.1:5000**.

For Streamlit Community Cloud, create a new app from this repository, set the
main file to `streamlit_app.py`, and use `requirements.txt` for dependencies.

## Structure

```

├── train_model.py           # trains LogisticRegression + RandomForest, exports metrics/model

├── streamlit_app.py         # Streamlit dashboard and patient assessment UI

├── templates/

│   └── predict.html         # intake form + live result panel
└── static/
    ├── css/style.css
    └── js/{dashboard,predict}.js
```

## How it works

- **Model**: logistic regression on standardized features (chosen for
  interpretability, per the project brief) is the deployed model. A random
  forest is trained separately only to produce the global feature-importance
  chart on the dashboard.
- **Explainability**: each prediction shows (1) the top contributing
  features, ranked by `|coefficient × standardized value|`, and (2) which of
  the brief's clinical thresholds (fever ≥38°C, fever ≥3 days, platelets
  <150,000, WBC <4,000) the patient trips — a transparent, non-black-box
  view a clinician can sanity-check.
- **`/api/predict`** takes the form's JSON and returns
  `{prediction, probability, risk_level, contributors, clinical_flags}`,
  which `predict.js` renders into the gauge and factor list without a full
  page reload.

## A note on the data

`train_model.py` drops exact duplicate rows before training (the raw CSV had
some), which is why accuracy comes out around 96% rather than the ~100%
figures in the original notebook — that 100% came from a mix of duplicate
rows and thresholds so clean-cut they left almost no overlap between classes.
Worth keeping in mind if this ever moves past a decision-support prototype:
a model that separates the classes *this* cleanly is worth double-checking
against how the labels were actually generated before trusting it on new,
messier patients.

## Retraining

Re-run `python train_model.py` any time `dataset.csv` changes — it rewrites
everything under `model/`. Restart `app.py` afterwards to pick up the new
model.
